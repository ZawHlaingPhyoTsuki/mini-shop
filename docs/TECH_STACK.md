# Technology Stack

This document records the intended stack based on the current `package.json`. Confirm provider-specific APIs against current documentation before implementation, especially because some dependencies are release candidates or beta versions.

## Application

### TanStack Start

Provides the full-stack React application framework, integrated routing, and server-side capabilities. Keep public storefront routes and authenticated dashboard routes in the same application initially.

### TanStack Router

Owns route definitions, route parameters, search parameters, and route-level data/loading patterns. Prefer typed route parameters and validated search parameters.

### React + TypeScript + Vite

Build the user interface and development/build workflow. Keep strict typing enabled and validate external data at runtime.

### Nitro

TanStack Start builds through Nitro and deploys to Vercel without a custom
adapter. Vercel runs the Node.js server output; Bun installs dependencies and
runs the build.

## Data

### Neon Postgres

Primary relational database for users' application data, shops, products, variants, inventory, orders, favorites, and reviews.

### Prisma 7

Type-safe database schema and queries. The project pins `prisma`, `@prisma/client`,
and `@prisma/adapter-pg` to exactly `7.10.1`; the npm `latest` tag points at an
8.x release candidate, so never widen the range. The schema lives in `prisma/`,
the CLI is configured in `prisma.config.ts`, and the Rust-free client is
generated into `src/generated/prisma` (gitignored, regenerated by
`bun run db:generate`). Migrations need the direct `DATABASE_URL_UNPOOLED`
connection; `migrate dev` also needs a shadow database.

### Money and localization

Money is stored as whole integer units plus an explicit currency. `MMK` and
`THB` both use zero decimal places in this market. Shared Zod schemas and `Intl`
formatting live under `src/domain/shared/`. English and Myanmar names are stored
in localized maps; adding Shan later means extending the shared locale list, not
adding database columns.

### Database workflow

- `db:push`: useful for local prototyping when appropriate.
- `db:generate`: generate migration files for review.
- `db:migrate`: apply migrations.
- `db:studio`: inspect data/schema.

For shared and production databases, prefer reviewed, version-controlled migrations. Do not casually use schema push against production.

## Authentication

### Better Auth

Handles identity, sessions, and authentication flows. Its Prisma adapter integrates authentication persistence with the database. The auth models are generated into `prisma/auth.prisma` and hand-tuned afterwards.

Application-specific roles and shop membership still need explicit authorization logic. A valid session alone does not grant permission to manage a shop or access an order.

The `auth:generate` script in `package.json` uses Varlock and a command-line generator. Verify the exact generator package, command, and generated output before relying on it; keep generated auth schema changes under review.

## Object storage

### Neon S3-compatible object storage + AWS SDK

Use `@aws-sdk/client-s3` and `@aws-sdk/s3-request-presigner` directly against
the Neon S3-compatible endpoint. This matches the `tcl-guide` setup:

- `forcePathStyle: true`
- server-generated object keys
- five-minute presigned `PUT` uploads
- a `public_read` bucket declared in `neon.ts`
- public URLs derived from the endpoint and bucket name

Store product-image objects outside Postgres and keep object keys plus metadata
in relational tables. Keep access keys server-side. Confirm endpoint, region,
bucket permissions, and maximum file size from current Neon documentation.
Do not add a second file abstraction.

## Forms, validation, and data fetching

- **TanStack Form:** complex product, shop, and checkout forms.
- **Zod:** validate form input and server-function payloads at runtime.
- **TanStack Query:** use for client-side asynchronous data and cache management where it complements Start's route/server data model. Avoid duplicate fetching/caching patterns without a clear need.

## UI

- **Tailwind CSS v4:** styling.
- **shadcn / Base UI:** accessible UI primitives and components; verify the project's actual component-generation conventions before adding components.
- **Lucide React:** icons.
- **Sonner:** toast notifications.
- **Inter variable font:** typography.
- **next-themes:** present in dependencies; confirm its integration and whether theme switching is in scope before wiring it into the app.

## Environment and quality

- **Bun:** package manager/runtime pinned in `package.json`.
- **Varlock:** environment variable management and code generation.
- **Oxlint:** linting.
- **Oxfmt:** formatting.
- **TypeScript:** static type checking.
- **Vitest + Testing Library + jsdom:** unit tests run in Node by default; add
  jsdom per file only for React rendering tests.

## Architectural approach

Start with a modular monolith. Keep domain modules separate by responsibility—auth, shops, catalog, media, orders, and admin—but do not split into microservices. PostgreSQL transactions and explicit authorization are more valuable for the MVP than distributed infrastructure.

## Items to verify before production
